# Module 04 — User Dashboard & Frontend

## Purpose
The main product surface. Renders GEX data for a user's allowed symbols, with views that differ by tier (free vs paid).

## Pages
- `/home` — landing after login: nav to Dashboard, Upgrade Subscription, Logout (Admin sees "Admin" link instead of dashboard nav).
- `/dashboard` — main GEX viewing app.
- `/upgrade` — Stripe Checkout entry (Module 06).

## Dashboard behavior by tier

### Free tier
- Symbols: SPY, QQQ (index-type view), TSLA, NVDA (stock-type view).
- **Index view** (SPY, QQQ): selector for Intraday / Weekly / Monthly. ("Intraday" is 0DTE-only — see Module 02's Granularity definitions; there is no separate "nearest active contract" concept anymore. **The "GEX Next 3 Trading Days" card (formerly "EOD GEX Analysis," formerly "1DTE/2DTE/3DTE") is paid-only entirely and does not appear for free users on SPY/QQQ**, even though those are otherwise free-tier symbols; see the dedicated component description below.)
- **Stock view** (TSLA, NVDA): weekly expiry only. The weekly card for stock symbols shows a **4-tab pill toggle: Past Week | This Week | Next Week | Week+2** — all 4 tabs are available to free users on TSLA/NVDA (confirmed override of the earlier "current week only for free" rule). Each tab shows the full per-strike GEX chart for that specific Friday expiry (or last trading day of that week), updated with the latest available `trade_date` snapshot for that expiry. View rolls forward after Friday close or 3:00 PM CT (enforce server-side).
  - **Tab windows, defined server-side in Central Time:**
    - **Past Week** — the Friday expiry that has just passed (1 week back)
    - **This Week** — the nearest upcoming/active Friday expiry
    - **Next Week** — the Friday expiry one week forward
    - **Week+2** — the Friday expiry two weeks forward
  - **Free users:** all 4 tabs available on TSLA/NVDA. Beyond these 4 windows (e.g. week+3, week+4..., or more than 1 week back historically) is still paid-only.
  - **Paid users:** all 4 tabs plus the full date picker for arbitrary historical lookback and further-out weeks (up to all 12 tracked via the sliding window).
  - **"12-Week Comparison" mode** (item 2's separate dropdown option) remains accessible alongside this toggle — it's a different view mode showing all tracked weeks as multiple series simultaneously, not the same as this tab-based single-week browsing. Both exist on the same card.
- The **Past Week tab** is the only historical access free users get on stock symbols — they cannot use the date picker to browse further back. Paid users get full history via the date picker in addition to the 4-tab shortcut.

### Paid tier
- Full symbol list: Mag7 (AAPL, MSFT, GOOGL, AMZN, NVDA, META, TSLA) + SPX + SPY, QQQ, IWM, NDX.
- All granularities: Intraday (0DTE only, see Module 02), weekly, monthly OPEX, rolling 21-day EOD trend.
- **"GEX Next 3 Trading Days" card** (renamed from "EOD GEX Analysis" — index symbols only — SPX, NDX, SPY, QQQ, IWM) — see dedicated UI component description below. Paid-only regardless of symbol, including SPY/QQQ.
- Full historical lookback (date picker) — for stock symbols, paid users additionally get the full 12-week forward window and arbitrary historical lookback beyond the 4 tabs that free users get. The differentiators from free are: (a) more than 1 week back historically, (b) more than 2 weeks forward (week+3 and beyond, up to 12 tracked). The 4-tab shortcut (Past Week | This Week | Next Week | Week+2) is also shown to paid users as a convenience, with the full date picker available alongside it.

## UI components
1. **Symbol selector** — dropdown or tab strip; only shows symbols the user's tier allows (paid sees full list; free sees 4, with the other 16 shown grayed out + "Upgrade to unlock" tooltip — good upsell surface). **Default symbol on first visit (no URL params): `SPY`** — not AAPL, not whatever the code previously defaulted to. SPY is a free-tier index symbol accessible to every user type; AAPL is paid-only and breaks for free users. On subsequent visits, the URL param restores the last-viewed symbol automatically (see "Dashboard state persistence via URL params" section below).
2. **Granularity selector** — Intraday (0DTE only) / weekly / monthly / rolling 21-day, contextual to whether the symbol is index or stock type. **For Mag7 stocks, "Intraday" is only meaningful on Fridays** (their only same-day-expiry day) — see the dedicated edge case below for how to handle Monday–Thursday. **Note: 1DTE/2DTE/3DTE are no longer selector options at all** — that functionality moved to the standalone "GEX Next 3 Trading Days" card (item 9 below), which isn't part of this dropdown.
   - **New view mode within Weekly and Monthly: "12-Week Comparison" / "3-Month Comparison."** Both Weekly and Monthly granularities now have two view modes:
     - **"This Week" / "This Cycle"** (existing, unchanged) — single tracked week/cycle, full per-strike detail, date-picker steps through `trade_date`s within it. Paid-only beyond the current week/cycle (existing rule, unchanged — see item 3 and test matrix case #26).
     - **"12-Week Comparison" / "3-Month Comparison"** (new) — full per-strike detail across multiple tracked weeks/cycles simultaneously, rendered as multiple series on the main GEX chart (item 4 below), one series per tracked week/month. **Free + paid — but with two separate restrictions:** (a) still symbol-restricted (free users get this only on their 4 free-tier symbols; SPX/AAPL/etc. still 403 for free users); (b) **free users on stock symbols (TSLA/NVDA) are capped at the next 3 upcoming weeks** in this mode, not all 12 — paid users see all 12 weeks / all 3 monthly cycles. Free users on index symbols (SPY/QQQ) in this mode: the "comparison" carve-out for stocks doesn't automatically extend to indexes — this is a stocks-specific feature per the confirmed decision; index symbol behavior in comparison mode should default to whatever the existing paid-only rules dictate (confirm if you want free users on SPY/QQQ to also get 3-week comparison or not — currently assumed not).
   - **⚠️ Naming collision risk — read carefully:** item 6 below is already a card literally named **"GEX Next 12 Weeks"** (a simple net-GEX trend line, no per-strike detail). This new "12-Week Comparison" mode is a **different, separate feature** — full per-strike multi-series detail, lives inside the Weekly granularity dropdown rather than as its own card. Use visibly distinct labels in the actual UI (e.g. keep item 6's card titled "GEX Next 12 Weeks," and label this dropdown option something like "12-Week Comparison" or "Compare Next 12 Weeks" — anything that doesn't read as the same feature) so users and future developers don't conflate the two. **This is a deliberate, twice-confirmed exception to the existing next-week-is-paid-only rule** — full per-strike data beyond the current week is normally paid-only (see item 3), but this specific multi-week comparison mode is an intentional carve-out, not a bug. The original single-week date-picker behavior is completely unchanged by this addition.
3. **Date picker / week selector** — behavior differs by symbol type and tier:
   - **Index symbols (all users):** full calendar for paid; free users on SPY/QQQ get the standard "current week" indicator.
   - **Stock symbols — the 4-tab pill toggle replaces the date picker as the primary navigation control** (see Free tier description above): all users see Past Week | This Week | Next Week | Week+2 tabs on the weekly GEX card for that stock, with paid users additionally having the full date picker available for arbitrary historical lookback and weeks beyond Week+2. The tabs show the latest available `trade_date` snapshot for each expiry week by default; stepping through individual `trade_date`s within a week (Mon/Tue/Wed/Thu for day-by-day evolution) is available to paid users via the date picker but not surfaced as tabs (too granular for the tab UI).
   - **Monthly granularity (all symbols):** paid users can step through any of the M tracked cycles and any `trade_date` within each; free users only get the forward-trend summary (item 10), no per-strike date picker at all.
   - (Monthly OPEX full detail is paid-only entirely, so none of the stock-tab nuance applies there — only items 6 and 10 are free-accessible for Monthly.)
4. **GEX chart** — strike-by-strike bar/line chart (call GEX vs put GEX), with call wall / put wall marked, and a **vertical dashed line at spot price** labeled with the actual value (e.g. "Spot: 5,432"). Recommend Chart.js or Plotly (Bootstrap-compatible, simple to wire to JSON endpoint). **Must fully re-render on every symbol/granularity/date change** — see the "switching the selector" edge case below for the specific failure mode this is guarding against. **Must also support multi-series rendering** when the "12-Week Comparison" / "3-Month Comparison" mode (item 2 above) is active — one distinct series per tracked week/month, clearly distinguishable (color/legend per tracked expiry date, not generic "series 1/2/3"). This is a materially different rendering mode from the single-snapshot bar chart used elsewhere, so budget real design/implementation time for it rather than assuming the existing single-series chart trivially extends.

   **Intraday time selection — snapshot picker for the 0DTE view.** When the Intraday granularity is active, a row of up to 10 clickable time boxes appears above or below the chart, each showing the actual Central Time of a captured snapshot (e.g. "8:45 AM", "9:00 AM", "2:30 PM"). Clicking a box replaces the chart with that snapshot's data — same single-series replace-not-overlay behavior as the Weekly tab toggle, not a multi-series comparison. No page reload; the chart updates via the existing `/api/gex` endpoint with a `timestamp` param.
   - **What's shown:** the 10 most recent snapshots for the selected symbol and trade date, ordered chronologically (earliest left, latest right). If fewer than 10 exist (e.g. early in the trading day), show however many are available.
   - **Default selected:** always the latest (rightmost) box on load, or when switching symbols/dates.
   - **Auto-update during market hours:** if the dashboard is open during market hours, a new snapshot arrives every `gex_0dte_interval_minutes` (default 15). When a new one arrives, the time box row updates (shifts left if already at 10, adds the new time on the right) and the chart auto-refreshes to the latest — **unless the user has manually selected an earlier box**, in which case the user's selection persists and the new box is added without auto-switching to it. A subtle indicator (e.g. a pulsing dot or "New snapshot available" text near the row) can surface that newer data exists.
   - **Tier:** same access as the existing Intraday view — free users get SPY/QQQ, paid users get all index symbols (SPX/NDX/SPY/QQQ/IWM). Stock symbols (Mag7) only show the intraday view on Fridays regardless; the time boxes appear/disappear accordingly.
   - **Labeling:** actual Central Time clock times only (e.g. "2:30 PM" not "-30m") — consistent with the "actual dates not relative labels" principle elsewhere in the dashboard. Append "CT" if space allows, or include it in a tooltip.
5. **Summary panel** — net GEX, call wall level, put wall level, spot price, and a **"last updated" timestamp from this snapshot's own `timestamp` field** (not a page-load time — see item 11 below).
6. **"GEX Next 12 Weeks" chart — available to free AND paid users, on any symbol they otherwise have access to.** Single trend-line chart: `net_gex` (and optionally `call_wall`/`put_wall`) plotted across the N tracked upcoming weeks (default `platform_settings.gex_weekly_forward_weeks`, 12) as of today — "how does the GEX picture differ between this week, 5 weeks out, and 12 weeks out" at a glance. **Positioned above item 7 (Rolling 21-Day Net GEX Trend)** — this specific ordering is required, not incidental. **Repurposes the dashboard slot previously occupied by a broken/empty "EOD GEX Analysis (historical)" card** — that card never displayed data; rather than debug it, it's being replaced outright by this feature. **This is deliberately a coarser view than the full per-strike detail (item 3's date picker) — no `gex_by_strike` breakdown here, just the net/wall summary numbers per tracked week. Note: free users on stock symbols now also have access to per-strike detail for the 4-tab window (Past/This/Next/Week+2) via the weekly card itself — this trend chart is still the broader 12-week summary view that goes further out than those 4 tabs. X-axis is each tracked week's actual expiry date — don't label points "week 1"/"week 2", etc.
7. **"Rolling 21-Day Net GEX Trend" chart** (renamed from "Net GEX trend strip" / 5-day — window widened to 21 trading days, see Module 02/03), paid only (or a teaser/blurred version for free, to upsell). **Placement exception to item 11's general rule:** this chart's "last updated" timestamp must sit **directly below the heading "Rolling 21-Day Net GEX Trend"**, not beside/next to the heading on the same line — the inline placement was crowding the heading and reading as part of the title rather than as a separate freshness indicator. This placement fix applies to this chart specifically, not the other charts/cards covered by item 11.
8. **Parallel coordinates view (paid only)** — compares individual option contracts (not aggregated per-strike data) across multiple expiries. **Axes: Strike, GEX, Expiry Date, Volume, Open Interest, Option Type (Call/Put)** — six dimensions, one line per contract leg.
   - **Index symbols** — unchanged from before: sources from whatever expiries are available in the underlying raw chain pull for that symbol, which already spans multiple expiry dates at once. Working as intended, no change needed.
   - **Mag7 stocks — data source and scope:** for stocks, sources from `gex_weekly` spanning **all N tracked upcoming weeks** (default 12), regardless of which week tab is currently selected in the Weekly GEX card. **This is the key decoupling requirement:** the 4-tab pill toggle (Past Week | This Week | Next Week | Week+2) on the Weekly GEX card controls only the Weekly GEX chart (item 4's single-week single-series view) — it must have **no effect** on the parallel coordinates chart, which always shows all tracked weeks simultaneously. These are independent pieces of state — the weekly tab selection is local to the Weekly GEX chart component and must not be passed to or read by the parallel coordinates component. If the current implementation shares state between them, the fix is to give each component its own isolated data fetch rather than sharing a selected-week variable. The Weekly/Monthly toggle (for switching between `gex_weekly` and `gex_monthly_opex` as the data source) remains; only the within-weekly week-selection is decoupled.
   - **Weekly/Monthly toggle (stocks only):** add an explicit **Weekly (12 weeks) / Monthly (3 cycles)** control above the chart for stock symbols, letting the user choose which tracked dataset feeds it. This control doesn't apply to index symbols (they keep the existing single chain-pull-sourced view with no toggle).
   - **Call/Put filter (required, not optional):** add an explicit **All / Calls only / Puts only** control above the chart, filtering the underlying dataset before it's rendered — not just relying on color or the Option Type axis. Putting Call/Put on a shared axis forces every line toward one of two points, which is what was producing the dense, hard-to-read crossing pattern in earlier versions of this chart. The filter actually subsets the data, which is what fixes legibility; color-coding alone doesn't.
   - **When a single side is selected (Calls only or Puts only), drop the Option Type axis entirely** — with only one value possible, that axis is dead space once filtered. Only show it when "All" is selected, where it's still useful in combination with color.
   - **Data requirements this surfaces (see Module 03):** this view needs per-contract `volume`, which the existing `gex_by_strike.call_greeks`/`put_greeks` shape doesn't currently store (it has `open_interest` per side but not `volume`) — add it. This applies to whichever source feeds the chart (raw chain pull for index, `gex_weekly`/`gex_monthly_opex` for stocks per the fix above).
   - Power-user/analyst tool, not needed for the core "what's the GEX today" use case — reserved for paid because it's denser, more compute/render-heavy, and the kind of feature that differentiates serious traders rather than something a casual free user would miss. Recommend Plotly (`plotly.graph_objects.Parcoords`) — it also natively supports drag-to-select/brush filtering on any axis, which is a useful secondary interaction in addition to the explicit toggle above (don't rely on it alone, since it's not very discoverable).
9. **"GEX Next 3 Trading Days" card (renamed from "EOD GEX Analysis" — paid only, index symbols only — SPX, NDX, SPY, QQQ, IWM)** — the original "next 3 upcoming trading days" term structure feature, renamed to actually reflect what it holds (parallel naming to item 6's "GEX Next 12 Weeks"). **Stays in its current position on the dashboard — not being relocated.** This is a distinct, separate card from item 6 — don't conflate or merge them; item 6 took over a different (previously broken) card's slot, this one is unaffected by that change and keeps its existing place. Shows the **next 3 upcoming trading days'** GEX side by side, as either 3 charts or 3 tables (user-toggleable chart/table switch, same data either way) — each panel titled by its **actual expiration date** (e.g. "Jun 25, 2026"), never by a "1DTE"/"2DTE"/"3DTE" label, since that terminology has been removed from the UI entirely. Data comes from `gex_intraday`'s embedded `term_structure` field (Module 02/03) — same option chain pull as the 0DTE data, same interval, not a separate fetch/job. Always shows the latest available data (live during market hours, last-captured value outside market hours — never blank/erroring on weekends or holidays). Trading-day math (not calendar-day) determines which 3 dates appear — see Module 02 for the holiday/weekend-skipping logic. Not available for Mag7 stocks at all (index-only feature) and not available to free users on any symbol, including SPY/QQQ.
   - **Strike range filter (all index symbols):** only display strikes within ±`gex_term_structure_strike_range_pct`% of the current spot price (default ±7%, admin-configurable via `platform_settings` — Module 03/05). For example, with SPY spot at 590 and a 7% threshold, only strikes between 548 and 631 are shown. This applies to all 3 panels simultaneously. Enforced **server-side** in `/api/gex/term-structure` — the filtered `gex_by_strike` array is returned, not the full unfiltered one with client-side hiding. This avoids sending unnecessary data over the wire and prevents a paid user from inspecting the full strike range in network requests.
10. **"Monthly OPEX Forward Trend" chart — available to free AND paid users, on any symbol they otherwise have access to.** Same pattern as item 6, but for the M tracked upcoming monthly OPEX cycles (default `platform_settings.gex_monthly_forward_cycles`, 3) instead of weeks. Not given a specific required placement (unlike item 6) — position wherever makes sense alongside the other monthly-granularity content.
11. **Data freshness indicator — every chart and card, no exceptions.** Each of items 4–10 above (GEX chart, GEX Next 12 Weeks chart, Rolling 21-Day Net GEX Trend chart, parallel coordinates view, GEX Next 3 Trading Days panels, Monthly OPEX Forward Trend chart, and the summary panel) must display when its underlying data was last refreshed — e.g. "Last updated: 2:47 PM CT" or a relative form ("Updated 3 min ago"), sourced from that data's own `timestamp`/`created_at` field (Module 03), not a generic "page loaded at" time. **Exact placement may vary per component** (see item 7's specific placement requirement for the Rolling 21-Day chart) — the requirement is that the timestamp exists and reflects that component's own data, not a specific universal position. This matters specifically because different parts of the dashboard can legitimately be stale by different amounts at the same moment — e.g. the main GEX chart might be 2 minutes old (last 0DTE tick) while the GEX Next 3 Trading Days card is also just-refreshed (same pull) but a Weekly view might be showing Monday's snapshot on a Wednesday by design (Module 02's evolution model) — a single global "last updated" timestamp for the whole page would be misleading in that case, since it would imply everything on screen is equally fresh when it isn't. Each component's freshness label should reflect its own data's actual timestamp.

## API endpoints (consumed by frontend JS)
| Endpoint | Auth | Description |
|---|---|---|
| `GET /api/symbols` | Yes | Returns allowed symbol list for current user's tier |
| `GET /api/gex?symbol=X&type=intraday&date=YYYY-MM-DD` | Yes | Returns the day's 0DTE intraday series as JSON. For Mag7 stocks on a non-Friday date, returns the "no intraday data — same-day expiry only exists on Fridays for this symbol" response rather than an empty series (see edge cases) |
| `GET /api/gex/intraday-snapshots?symbol=X&date=YYYY-MM-DD&n=10` | Yes | Returns metadata (timestamp, net_gex, call_wall, put_wall, spot_price) for the last N intraday snapshots for the given symbol/date, ordered chronologically. Default N=10, max 10 for v1. Used to populate the time selection box row — does NOT return gex_by_strike (that's fetched separately when a box is clicked). Same tier/symbol restrictions as the main intraday endpoint. |
| `GET /api/gex?symbol=X&type=intraday&date=YYYY-MM-DD&timestamp=HH:MM` | Yes | Returns the full snapshot (including gex_by_strike) for the specific timestamp clicked. `timestamp` is a Central Time time string matching one of the values returned by `/api/gex/intraday-snapshots`. |
| `GET /api/gex/rolling?symbol=X` | Yes (paid) | Returns rolling 21-day series (renamed from 5-day — see Module 02/03) |
| `GET /api/gex/greeks?symbol=X&option_type=all\|call\|put&source=chain\|weekly\|monthly` | Yes (paid) | Returns per-contract data for the parallel coordinates view: `strike`, `gex`, `expiry_date`, `volume`, `open_interest`, `option_type` — one record per contract leg. **`source` param:** `chain` (default for index symbols) reads the raw multi-expiry chain pull; `weekly`/`monthly` (stocks only — see Module 04's parallel coordinates description) read from `gex_weekly`'s 12 tracked weeks or `gex_monthly_opex`'s 3 tracked cycles instead, which is the fix for stocks only ever showing their current week's expiry under the old chain-pull-only approach. `option_type` filters server-side to match the dashboard's All/Calls/Puts toggle — don't fetch everything and filter client-side, since that defeats the point of the filter for large chains. Despite the endpoint's name, this is no longer "just greeks" (it currently doesn't even return greeks in this view) — consider renaming to `/api/gex/chain-detail` or similar if that's clearer, though not required |
| `GET /api/gex/term-structure?symbol=X` | Yes (paid) | Returns the latest `term_structure` array (next 3 trading days' GEX) for the "GEX Next 3 Trading Days" card — index symbols only. **Server-side filters `gex_by_strike` to strikes within ±`gex_term_structure_strike_range_pct`% of the current spot price** (from `platform_settings`, default ±7%) before returning — the full unfiltered strike array is never sent to the client |
| `GET /api/gex/weekly-trend?symbol=X` | Yes (free + paid) | Returns the net GEX/wall summary (no per-strike detail) across all N tracked upcoming weeks, for the "GEX Next 12 Weeks" chart |
| `GET /api/gex/monthly-trend?symbol=X` | Yes (free + paid) | Returns the net GEX/wall summary (no per-strike detail) across all M tracked upcoming monthly cycles, for the "Monthly OPEX Forward Trend" chart |
| `GET /api/gex/weekly-comparison?symbol=X&weeks=N` | Yes (free + paid, symbol-restricted) | **New, distinct from `weekly-trend` above.** Returns FULL per-strike detail (`gex_by_strike` included) for EACH of the N tracked weeks — an array of N full snapshot objects, not a summary. Powers the "12-Week Comparison" granularity mode (item 2). Optional `weeks` param: paid users can request up to 12; free users on stock symbols are server-side capped at 3 regardless of what `weeks` they request — enforce this cap server-side, not just via the UI dropdown. Free-accessible but still enforces the existing free-tier symbol list — see the authorization note below, this one is easy to implement incorrectly |
| `GET /api/gex/monthly-comparison?symbol=X` | Yes (free + paid, symbol-restricted) | Same pattern as `weekly-comparison`, for the M tracked monthly cycles. Powers the "3-Month Comparison" granularity mode |
| `GET /api/gex/public?symbol=X&date=YYYY-MM-DD` | No | Single read-only snapshot for Twitter-link landing (Module 08) — rate-limited, no auth |

All endpoints enforce tier/symbol authorization **server-side** (never trust the frontend dropdown alone — a free user hitting `/api/gex?symbol=NVDA&type=monthly` directly should get a 403, since monthly granularity isn't in their tier even though NVDA itself might be visible at weekly). This applies to `/api/gex/greeks` too — a free user hitting it directly for any symbol, including their own free-tier ones, should get a 403, since this endpoint is paid-only regardless of symbol. **Same rule for `/api/gex/term-structure`: a free user hitting it directly for SPY or QQQ (their own free-tier symbols) must still get a 403** — this card is paid-only regardless of symbol, and a Mag7 stock symbol on this endpoint should get a 404/400 (not applicable to stocks at all, a different failure mode than the tier check).

**`/api/gex/weekly-trend` and `/api/gex/monthly-trend` are the one deliberate exception — these ARE accessible to free users**, but the implementation needs to get the *shape* of that access right, not just the status code: the response for a free user must omit `gex_by_strike` entirely (or any other per-strike data) regardless of which symbol or week/cycle is being summarized — only `net_gex`/`call_wall`/`put_wall` per tracked expiry. **Do not implement this by reusing the same underlying query that powers the paid full-detail view and just stripping fields client-side** — fetch only the summary fields server-side, so a free user inspecting network requests can't see the full per-strike payload even briefly before any client-side filtering. This is the same principle as never trusting the frontend for authorization, applied to data shape rather than access — a free user should never receive `gex_by_strike` in the response body at all, paid or not, on these two specific endpoints.

**`/api/gex/weekly-comparison` and `/api/gex/monthly-comparison` are a second, different kind of exception — read this carefully, it's the easiest thing in this doc to implement wrong.** Unlike `weekly-trend` (summary only, no per-strike data, ever), these DO return full `gex_by_strike` per-strike data to free users — but only for their existing free-tier symbol list, and the existing "is this beyond current week" check must be **bypassed specifically for these two endpoints** while the existing "is this symbol in this user's tier" check must **still apply unchanged**. Concretely:
- ✅ Free user, `weekly-comparison?symbol=SPY` → 200 with full per-strike detail across all 12 weeks (the new carve-out)
- ✅ Free user, `weekly-comparison?symbol=AAPL` → 403 (symbol restriction still applies — AAPL was never free-tier)
- ✅ Free user, `GET /api/gex?symbol=SPY&type=weekly&date=<5 weeks out>` (the *original* single-week endpoint, NOT this new one) → still 403, completely unchanged (test matrix case #26)
- ❌ **Bug to avoid:** implementing this by reusing the same authorization function as the original weekly endpoint, which would incorrectly 403 case 1 above (since that function's whole job is enforcing the next-week-paid-only rule this endpoint is deliberately exempt from)
- ❌ **Bug to avoid (the opposite mistake):** loosening the original weekly endpoint's authorization to accommodate this, which would incorrectly flip case 3 from 403 to 200 (a real regression of an existing, tested rule)
The clean way to implement this: a **separate authorization check for these two endpoints specifically** — symbol-tier check only, no week-distance check — rather than modifying or reusing the existing week-distance-aware check at all.

**`date` param semantics for `type=weekly`:** `date` means `trade_date` (the day the snapshot was taken — Monday through Friday), not `expiry_date` (the Friday being forecasted toward) — see Module 02/03. To select which expiry week (tab), use a separate `expiry_date` param. Omitting both defaults to the latest available `trade_date` for the current/nearest week. **Authorization for free users on stocks:** the allowed `expiry_date` range is the 4-tab window — past week, this week, next week, and week+2 (confirmed override of the old "current week only" rule). Beyond week+2 forward or more than 1 week back is 403. Stepping through individual `trade_date`s within a week (Mon/Tue/Wed/Thu) is available to paid users only, not surfaced in the free-tier 4-tab UI.

**`date` param semantics for `type=monthly`:** same pattern as weekly — `date` means `trade_date` (a Monday or Friday), not `expiry_date`. Since this granularity is paid-only entirely, there's no free-tier nuance here, but the read path still needs to handle the rollover case correctly: a query for "today's" monthly snapshot on an actual 3rd-Friday-expiry day should return the *new* cycle's first point (the one with the rolled-forward `expiry_date`), not the just-expired cycle's last point — see Module 02/03 for the rollover logic this read path needs to be aware of.

**Authorization logic for the 4-tab stock weekly toggle — this replaces the earlier "next-week-is-403-for-free" rule for stocks specifically.** The check must now verify whether the requested `expiry_date` falls within the 4 allowed windows for the user's tier: free users on stock symbols get Past Week / This Week / Next Week / Week+2 (confirmed override). Beyond that — week+3 or further forward, or more than 1 week back — is still 403 for free users. Paid users get the full range. This is still a date-range check, not just a symbol+granularity check — same principle as before, just with a wider allowed window for free users on stocks (4 expiry windows instead of 1).

## Tier authorization test matrix
Given how many free/paid boundary rules have accumulated across this module (next-week gating, paid-only features regardless of symbol, index-only features, within-week stepping restrictions), this is the canonical list to test **as a single pass** any time tier logic changes — not just the specific case that prompted the most recent change. ## Dashboard state persistence via URL params
When the dashboard page is refreshed (F5 / browser reload), it must restore the exact view the user was on — symbol, granularity, and selection within that granularity. The mechanism is **URL query params**, not localStorage, cookies, or server-side session — URL params survive refresh naturally, work correctly with browser back/forward, and are shareable (a user can bookmark or send a URL and it opens the same view).

### URL param schema

| Param | Values | Description |
|---|---|---|
| `symbol` | `SPY`, `TSLA`, `SPX`, etc. | Currently selected symbol |
| `type` | `intraday`, `weekly`, `monthly`, `rolling` | Currently selected granularity |
| `expiry` | `YYYY-MM-DD` | For `type=weekly`: the expiry_date of the selected week tab (Past/This/Next/Week+2 or a specific date for paid users). For `type=monthly`: the selected monthly cycle's expiry_date. Omit for `type=intraday` and `type=rolling`. |
| `ts` | `HH:MM` (CT, 24hr) | For `type=intraday` only: the selected time box (e.g. `14:30` for 2:30 PM CT). Omit for other granularities. |

Example URLs:
- `/dashboard?symbol=SPY&type=intraday&ts=14:30` — SPY, Intraday view, 2:30 PM snapshot selected
- `/dashboard?symbol=TSLA&type=weekly&expiry=2026-07-11` — TSLA, Weekly view, July 11 expiry tab
- `/dashboard?symbol=SPX&type=monthly&expiry=2026-07-17` — SPX, Monthly view, July cycle

### Behavior requirements

1. **On every state change** (symbol switch, granularity switch, week tab click, time box click) — update the URL using `history.replaceState()` without triggering a page reload. The URL updates silently in the background as the user navigates the dashboard.

2. **On page load / refresh** — read params from the URL first. If valid params are present, load that view directly. If params are absent (first visit, or no params), fall back to the **default view: `symbol=SPY&type=intraday`** — not AAPL, not whatever the code previously defaulted to. SPY is a free-tier symbol accessible to all users; AAPL is paid-only and produces an error for free users, which is why the current behavior is broken.

3. **Tier enforcement still applies on URL load** — a free user who bookmarks `/dashboard?symbol=SPX&type=intraday` should get the symbol-access-denied response (or be redirected to SPY with a message), not a bypass of the tier check. The URL is a hint to the frontend, not an authorization bypass. The same server-side checks that apply when changing the dropdown must also apply when restoring from URL.

4. **Invalid param values** — if a URL param contains an unrecognized symbol, an unsupported granularity type, or an expiry/timestamp that doesn't match any available data, fall back to the default view (`SPY/intraday`) rather than showing a broken/empty chart. Don't error on bad URL params.

5. **`ts` param on non-intraday views** — ignore silently (it's irrelevant when not in intraday mode). Similarly, ignore `expiry` when `type=intraday` or `type=rolling`.

### Implementation note
Use `history.replaceState()` (not `pushState`) for most state updates — replace rather than push, so that stepping back/forward through browser history moves between pages, not between every click within the dashboard. Exception: switching to a completely different symbol could reasonably use `pushState` so the user can press Back to return to their previous symbol. Either approach is acceptable; pick one and be consistent.
- Symbol has no data yet for the requested date (e.g. pipeline hasn't run yet today) → show "data not available yet, last updated: [timestamp]" rather than an empty chart.
- **Stale-but-present data should look visibly different from fresh data, not just report a timestamp the user has to read carefully.** If a chart's "last updated" (item 11 above) is significantly older than expected for the current time of day (e.g. an Intraday chart whose timestamp is from 2 hours ago during market hours, suggesting the pipeline may be stuck — see Module 07's scheduler liveness monitoring), consider a visual treatment (muted color, a small warning icon) in addition to the text timestamp — don't make "is this actually current" something the user has to do date-math on every time.
- **Mag7 stocks on the Intraday granularity, Monday–Thursday: this isn't a "not available yet" situation, it's "never available for this combination."** Since stocks only have a same-day-expiring contract on Fridays (Module 02), there is no intraday data to show the other four days, by design. Show a distinct message — e.g. "Intraday view is only available on Fridays for [symbol], when same-day options expire. Try Weekly instead." — rather than the generic "not available yet" message, since that implies the data is just delayed and will show up if the user waits/refreshes, which isn't true here.
- **Intraday time selection — fewer than 10 snapshots available** (e.g. before 10:45 AM CT on a 15-min interval, only a few snapshots exist): show however many boxes are available, don't pad with disabled/placeholder boxes. First box of the day is typically 8:45 AM CT; if the market just opened there may only be 1–2 boxes.
- **Intraday time selection — user has a specific box selected, new snapshot arrives:** add the new box to the right of the row and shift the leftmost off if already at 10, but do not auto-switch the chart to the new snapshot — preserve the user's explicit selection. Show a subtle indicator that newer data is available (e.g. a pulsing dot on the new rightmost box).
- **Intraday time selection — outside market hours** (evenings, weekends, non-trading days): show the time boxes from the last trading day's captures as a static, non-updating row (no auto-refresh polling needed outside market hours). The "latest" box remains the last-captured snapshot.
- Free user's session somehow has stale paid-symbol data cached client-side after a downgrade → always re-fetch `/api/symbols` on dashboard load, never cache tier client-side beyond the page session.
- The 4-tab pill toggle windows roll forward after Friday close or 3:00 PM CT (Module 03's Central Time standard) — compute server-side at request time, not cached at login. After rollover: what was "Next Week" becomes "This Week," "This Week" becomes "Past Week," and "Past Week" drops off (becomes 2 weeks ago, which is beyond the 1-week-back free limit and returns 403). A session spanning a Friday afternoon rollover must reflect the new windows without requiring re-login.
- **Switching the granularity selector (Intraday / Weekly / Monthly / etc.) or the symbol selector must trigger a fresh `/api/gex` fetch and a full chart re-render — not a partial update, and not a silent no-op.** This is a known easy-to-under-build interaction: a dropdown's `onChange` firing visually but not actually re-fetching, a backend route that ignores the `type` query param and just returns "latest snapshot for this symbol" regardless of requested granularity, or a chart library instance that's created once and never properly updated with new data are all common failure modes here, and they're easy to miss in manual testing if the data values happen to look plausible at a glance. Concretely:
  - The frontend must issue a distinct, observable network request (different `type`/`date` query params) every time either selector changes — verify this isn't being debounced/cached into a no-op.
  - The backend route handler must genuinely filter by the requested `snapshot_type`/`type` param against the correct collection (`gex_intraday` for the unified Intraday view, `gex_weekly` for weekly, `gex_monthly_opex` for monthly — see Module 03) — not just fetch "latest for symbol" and ignore the granularity entirely.
  - The chart component must be destroyed/recreated or explicitly `.update()`'d with the new dataset on every fetch — confirm this with a manual test: switch SPY between Intraday and Weekly and confirm the call wall / put wall / net GEX numbers in the summary panel visibly change, not just the chart's x-axis labels.
  - Write an automated test that hits `/api/gex` with the same symbol and two different `type` values and asserts the responses differ (different `snapshot_type` in the response, different `gex_by_strike` data) — this catches the backend half of this bug class even without a browser test.
